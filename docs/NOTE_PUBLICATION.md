# Bounded note publication without losing experiment history

The old worker sent every file under `experiments/BOT/` with each candidate.
The publisher treated that as one bounded transaction (128 files / 1 MiB), so
ordinary historical growth eventually stopped otherwise valid improvement jobs.
On 18 October, alpha had 133 historical files but only six edits (55,013 bytes);
gamma had 1,099,790 historical bytes but only six edits (216,215 bytes). Both
native results were READY_FOR_EVAL and exact-source checks had passed. Neither
had a publication intent or remote push.

Workers now send `notes_mode: delta-v1`, changed note files, and an explicit
`notes_deleted` list derived from the validated worktree diff against the frozen
input revision. The trusted publisher starts from that exact Git parent, keeps
unmentioned history byte-for-byte, and applies only those edits. Source remains
a complete validated immutable snapshot, not a patch. Generated bytecode stays
in private checkpoints and is excluded from publication.

The 128-edit / 1 MiB transaction and 256 KiB per-file limits remain. They apply
to the current experiment, not all accumulated history. A genuinely oversized
new edit still fails safely; the worker cannot disable limits, change another
lane, or smuggle an executable build recipe. The client also checks the complete
2 MiB mailbox envelope before writing it, so an oversized request cannot sit
waiting for a response to a message the server rejected as unsafe.

Older bounded snapshot clients retain their original `snapshot-v1` behavior;
all deployed server workers use delta-v1. Explicit deletions and moves are
honored only inside the assigned bot's experiment subtree. Symlinks, traversal,
unsupported artifacts, conflicts and ambiguous publication intents remain
blocked. Git and the original private checkpoint preserve prior versions; no
historical result is rewritten as a stronger score.

## Recovery and deployment

Pause scheduling, let any active model writer finish, then stop all services.
Install the committed runtime using `ops/upgrade.py`. Recover only the two
identified pre-push failures with the stopped-service administrator helper:

```bash
python3 /opt/battlecode/ops/recover-publication.py --bot alpha --task-id task-67604621e969459896026d5855132cae
python3 /opt/battlecode/ops/recover-publication.py --bot gamma --task-id task-ffac8b92c85645ca803df9d1120ffd48
```

Capture runs under each owner; SQLite writes and Git publication run under the
arena user. Recovery requires the exact saved READY_FOR_EVAL result, source that
previously passed a trusted check, unchanged input tip/base/engine identities,
server ownership, global pause, and no publication intent. It rechecks that exact
candidate and uses the normal publisher. It invokes no model, overwrites no old
owner result/checkpoint, and never retries a push of unknown outcome. The new
commit and recovery receipt remain attributable to the original task.

Restart the managed supervisor and send `arena start`. Frozen-opponent evaluation,
hourly improvement spacing, one model slot, rootless isolation, rolling raw-game
retention and the full champion gate are unchanged. Official actions remain
disabled. A controlled service restart is not evidence of provider reboot safety.

Regression checks include inherited history beyond both former limits, exact
preservation of unchanged bytes, note additions/deletions/moves, scope and symlink
denial, mailbox overflow rejection before writing, and recovery of both known
failure classes with zero additional model invocations.
